# Go + Redis + PostgreSQL: плюсы, минусы и границы решения

Этот файл — короткая памятка для защиты архитектуры на интервью. Подробный план реализации находится в `IMPLEMENTATION_SPEC_REDIS_GO_POSTGRES.md`.

## Решение

- Go API — stateless HTTP-сервис.
- Redis — оперативная дедупликация, rate limiting и bucketed counters.
- PostgreSQL — опросы, варианты, статусы и периодические/финальные результаты.
- Linux + Docker Compose — локальный запуск и демонстрация.

## Почему решение подходит

### Плюсы

| Плюс | Практический эффект |
|---|---|
| Быстрый горячий путь | Один атомарный Redis Lua call вместо SQL insert/index update на каждый голос |
| Простое масштабирование API | Реплики Go не хранят пользовательскую session state |
| Атомарная дедупликация | Проверка device key и увеличение нескольких счетчиков выполняются одной операцией |
| Контроль hot key | Счетчики разбиты на buckets и могут распределяться по Redis Cluster slots |
| Естественный TTL | Временные dedup-данные удаляются автоматически |
| Хорошее разделение ответственности | Redis принимает минутный всплеск, PostgreSQL хранит долговечное состояние |
| Небольшой dependency graph | Основной код строится на стандартной библиотеке Go; нужны только драйверы PostgreSQL и Redis |
| Реалистично за два дня | Можно закончить API, тесты, Compose и документацию без Kafka/Kubernetes |
| Хорошая демонстрация Middle+ навыков | Видны concurrency, idempotency, privacy, failure modes и нагрузочное мышление |

### Особенно удачные детали

- `participants_count` хранится отдельно от option counters, поэтому multiple choice считается корректно.
- Gate проверяется внутри Lua: stale cache API не позволяет голосовать после закрытия.
- Повтор запроса возвращает `already_recorded`: потерянный HTTP-ответ не приводит к двойному голосу.
- IP не является идентификатором избирателя, поэтому пользователи за NAT не блокируют друг друга.
- Redis Cluster hash tags согласованы с bucket: multi-key Lua остается возможным.

## Цена решения

### Минусы

| Минус | Последствие | Смягчение |
|---|---|---|
| Два хранилища вместо одного | Больше конфигурации и failure modes | Четко разделить ownership данных и покрыть integration tests |
| Redis временно является источником истины | При потере Redis возможна потеря еще не сохраненных голосов | AOF, replica/managed Redis, snapshots, retention |
| Eventual consistency результатов | PostgreSQL snapshot может отставать от live Redis | Показывать `source` и `as_of`, финализировать после close |
| Нет полного журнала голосов | Нельзя точно переиграть агрегацию или расследовать каждый голос | Для production добавить durable event log |
| Cookie dedup обходится | Очистка cookie/другой браузер дает новый голос | Это явно допустимый basic anti-abuse; добавить rate limit/CAPTCHA по риску |
| Bucket aggregation дороже одного GET | Results endpoint читает N hashes | Pipeline и короткий cache агрегированного ответа |
| Publish/close затрагивают N gates | Lifecycle сложнее одного status flag | Операции редкие, сделать их идемпотентными |
| Redis Lua требует аккуратного keyspace | Runtime error не откатывает предыдущие команды script | Валидировать вход до script и владеть типами всех ключей |
| Менять число buckets нельзя на лету | Возможны пропущенные totals | Хранить bucket count как часть runtime config poll |
| Операционная стоимость Redis Cluster | Реальный extreme scale требует managed/cluster setup | Не разворачивать cluster в тестовом, только показать путь |

## Главные риски

### 1. Неверная трактовка 100 млн

100 млн зрителей не равны 100 млн голосов. При 1% конверсии средняя нагрузка — около 16,7 тыс. RPS за минуту; при 100% — около 1,67 млн RPS без учета более высокого мгновенного пика.

Нельзя заявлять, что один Compose stack выдерживает верхнюю границу. Правильная позиция: дать воспроизводимый benchmark MVP и отдельно production scaling plan.

### 2. Потеря оперативных данных Redis

С AOF `everysec` существует небольшое окно потери при аварии. Возможные уровни усиления:

1. AOF + replica + periodic snapshots;
2. managed Redis с failover;
3. append accepted vote events в durable log;
4. Kafka/Pulsar и отдельная streaming architecture.

Чем строже требование «не потерять ни одного принятого голоса», тем менее достаточен Redis-only hot state.

### 3. Частичный close/finalization

Может получиться: gates уже закрыты, Redis totals прочитаны, PostgreSQL временно недоступен. Поэтому counters живут еще 24 часа, а close/finalize повторяется идемпотентно.

### 4. Ложная уверенность в анонимной дедупликации

Device cookie останавливает обычный повторный клик, но не мотивированную накрутку. Более сильная защита потребует хотя бы risk scoring, CAPTCHA, network/device signals либо регистрации — и создаст privacy/UX компромиссы.

### 5. Hot metadata и results

Даже если counters разбиты на buckets, чтение poll metadata или частый admin refresh может стать отдельным hot path. Поэтому immutable definition кэшируется в Go, а агрегированный result — на короткое время.

## Почему не PostgreSQL-only

PostgreSQL-only был бы проще и долговечнее, но каждый голос создает запись/уникальную проверку/WAL и нагружает connection pool. Это вполне разумный вариант при умеренной фактической конверсии, однако хуже демонстрирует работу с телевизионным всплеском.

Перейти обратно на PostgreSQL-only стоит, если измерения показывают небольшую нагрузку, нужен аудит каждого голоса и команда не хочет эксплуатировать Redis как критическое хранилище.

## Почему не Kafka сразу

Kafka дает durable log, replay и высокий throughput, но требует producer semantics, partitioning, consumer idempotency, aggregation, monitoring и еще одного хранилища дедупликации. За два дня высок риск не закончить главное.

Kafka становится оправданной, если одновременно нужны:

- подтвержденные сотни тысяч запросов в секунду;
- аудит каждого принятого события;
- повторный расчет;
- несколько downstream consumers;
- допустимая eventual consistency;
- команда умеет обслуживать streaming platform.

## Насколько хорош Linux + Redis

### Linux

Очень хороший выбор: стандартная production-среда для Go, Redis и PostgreSQL, предсказуемое контейнерное окружение, простой graceful shutdown и небольшие образы. Docker Compose достаточен для сдачи; Kubernetes для такого scope избыточен.

### Redis

Хороший выбор именно для короткого burst и временной дедупликации. Он перестает быть «просто кэшем» и становится критическим компонентом приема голосов, поэтому нужны:

- fail-closed поведение;
- AOF/replication;
- monitoring;
- TTL и retention;
- bucketed keys;
- ясный recovery plan.

### PostgreSQL

Нужен рядом с Redis. Хранить polls и финальные результаты только в Redis было бы хрупко, неудобно для admin queries и хуже объяснимо как долговременная модель.

## Что защищать на интервью

Короткая формулировка:

> Я оптимизировал не общий объем аудитории, а минутный write burst. Поэтому прием голоса — один атомарный Redis script, API stateless, счетчики шардированы, а PostgreSQL вынесен из hot path и хранит долговечное состояние. При этом я честно ограничил guarantee: cookie-dedup обходится, а строгая durable-доставка потребовала бы event log.

Хорошие акценты:

- почему один общий counter — hot key;
- почему dedup и counter должны изменяться атомарно;
- почему IP нельзя использовать как voter ID;
- почему fallback в PostgreSQL при сбое Redis создает split-brain;
- почему multiple choice требует отдельного participant counter;
- как повторно завершить оборвавшийся close;
- чем измеренный benchmark отличается от обещанной capacity.

## Когда архитектуру нужно пересмотреть

Выбрать PostgreSQL-only, если:

- фактическая нагрузка мала;
- требуется полный аудит;
- простота эксплуатации важнее latency burst;
- потеря даже секунды Redis state неприемлема, но Kafka избыточна.

Добавить durable event stream, если:

- нужны replay и несколько consumers;
- подтверждена очень высокая нагрузка;
- есть строгая гарантия сохранения принятого события;
- результаты могут считаться асинхронно.

Усилить identity/anti-abuse, если:

- результаты имеют юридические или финансовые последствия;
- появляется мотивированный атакующий;
- basic cookie/rate-limit перестают соответствовать риску.

## Итоговая оценка

Для двухдневного Middle+ тестового решение оценивается как сильный компромисс: оно достаточно простое, чтобы закончить и протестировать, но раскрывает ключевые проблемы высокой пиковой нагрузки. Его слабое место — durability и отсутствие полного event log, а не скорость Go API. Это ограничение нужно не скрывать, а сделать частью архитектурного обоснования.
