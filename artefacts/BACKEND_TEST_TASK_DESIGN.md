# Архитектура сервиса телевизионных опросов

## Краткий вывод

Для тестового задания на 2 дня я бы сделал небольшой, но законченный сервис:

- stateless API на Go;
- PostgreSQL для опросов, вариантов ответа, статусов и финальных результатов;
- Redis для дедупликации, rate limiting и быстрых счетчиков во время эфира;
- Docker Compose для локального запуска на Linux;
- миграции, unit/integration-тесты и один нагрузочный сценарий в k6;
- простую HTML-страницу голосования — только если после завершения backend остается время.

Linux + Redis — хороший выбор, но одного Redis недостаточно. Redis уместен на горячем пути голосования, а долговременные данные лучше хранить в PostgreSQL. Важно также не обещать, что один экземпляр Redis выдержит все 100 млн голосов за минуту: для такой верхней границы нужны шардирование, управляемая инфраструктура и отдельное нагрузочное проектирование.

## 1. Как я интерпретирую условие

100 млн зрителей — это размер аудитории, а не гарантированное число запросов. Перед реализацией в реальном проекте нужно уточнить ожидаемую конверсию, географию, допустимую потерю голосов и требуемую точность live-результатов.

Оценка средней нагрузки за минуту:

| Доля проголосовавших | Голосов | Средняя нагрузка | Возможный пик `x3` |
|---:|---:|---:|---:|
| 1% | 1 млн | ~16,7 тыс. RPS | ~50 тыс. RPS |
| 10% | 10 млн | ~166,7 тыс. RPS | ~500 тыс. RPS |
| 100% | 100 млн | ~1,67 млн RPS | ~5 млн RPS |

Для двухдневного тестового разумно:

1. реализовать корректный MVP;
2. измерить его на одном компьютере;
3. описать путь масштабирования;
4. не изображать production на миллионы RPS с помощью большого количества незавершенной инфраструктуры.

Основные функциональные предположения:

- опрос имеет время начала и окончания;
- поддерживаются `single_choice` и `multiple_choice`;
- голосовать можно без аккаунта;
- результаты доступны администратору;
- небольшая задержка live-результатов допустима;
- защита рассчитана на обычного пользователя, а не на мотивированного атакующего.

## 2. Варианты решения

### Вариант A. Только Go + PostgreSQL

Каждый голос сохраняется строкой в таблицу `votes`, а уникальный индекс `(poll_id, voter_hash)` не допускает повторного голоса.

Плюсы:

- самое простое и прозрачное решение;
- строгая долговечность и удобный аудит;
- дедупликация обеспечивается самой БД;
- легко писать SQL-запросы и пересчитывать результаты.

Минусы:

- интенсивная запись, уникальный индекс и обновление счетчиков становятся узким местом;
- соединения с БД и WAL плохо подходят для резкого телевизионного всплеска;
- горизонтальное масштабирование сложнее;
- хранение каждой попытки может быть избыточным.

Когда выбирать: если ожидается до нескольких тысяч голосов в секунду и важнее простота, чем запас по пиковому трафику.

### Вариант B. Go + Redis на горячем пути + PostgreSQL

API атомарно проверяет дедупликацию и увеличивает счетчик в Redis. PostgreSQL хранит конфигурацию опроса и периодические/финальные снимки результатов.

Плюсы:

- короткий и быстрый путь записи;
- TTL естественно очищает ключи дедупликации;
- легко реализовать rate limiting;
- API остается stateless и масштабируется репликами;
- хорошо укладывается в два дня.

Минусы:

- появляется второй stateful-компонент;
- нужно явно определить модель надежности Redis;
- live-результаты могут быть немного рассинхронизированы со снимком в PostgreSQL;
- один общий счетчик становится hot key;
- без журнала событий сложнее провести аудит и восстановить каждый голос.

Когда выбирать: это лучший компромисс для данного тестового.

### Вариант C. Go + очередь событий + отдельный агрегатор

API принимает голос и публикует событие в Kafka/Pulsar/NATS JetStream. Consumers выполняют дедупликацию, агрегацию и сохраняют результаты в хранилище.

Плюсы:

- хорошее горизонтальное масштабирование;
- сохраняется журнал голосов;
- можно повторно пересчитать результаты;
- прием запросов отделен от аналитики.

Минусы:

- заметно больше кода и инфраструктуры;
- сложнее exactly-once/idempotency, мониторинг и локальный запуск;
- за два дня велика вероятность получить красивую схему вместо надежного законченного решения.

Когда выбирать: для production-системы с подтвержденной нагрузкой в сотни тысяч RPS, требованиями к аудиту и отдельной платформенной командой.

### Краткое сравнение

| Подход | Сложность MVP | Пиковая запись | Надежность/аудит | Пригодность для 2 дней |
|---|---:|---:|---:|---:|
| PostgreSQL only | низкая | средняя | высокая | высокая |
| Redis + PostgreSQL | средняя | высокая | средняя/высокая | **оптимальная** |
| Event streaming | высокая | очень высокая | высокая | низкая |

По характеру нагрузки задача похожа не на обычную CRUD-админку, а на flash sale, сбор телеметрии или подсчет рекламных событий: короткое окно, много одинаковых дешевых операций и риск одного горячего ключа.

## 3. Рекомендуемая архитектура MVP

```text
Телефон зрителя
       |
   CDN / Load Balancer
       |
  несколько Go API instances
       |                 \
       |                  \ PostgreSQL
       |                    polls, options, admins,
       |                    result snapshots
       |
     Redis
  deduplication, rate limit,
  sharded live counters
```

CDN нужен прежде всего для статической страницы и ассетов. Запрос голосования нельзя кэшировать. Load balancer завершает TLS и распределяет запросы между stateless-репликами API.

### Компоненты

**Go API**

- публичная выдача активного опроса;
- прием голоса;
- создание и публикация опроса;
- просмотр результатов;
- валидация данных и административная авторизация.

Подходящие библиотеки: стандартный `net/http` или `chi`, `pgx`, Redis client, `golang-migrate`/Goose, `slog`. Чем меньше framework magic, тем проще проверять тестовое.

**PostgreSQL**

- источник истины для метаданных;
- хранение пользователей админки или одного заранее заданного admin token;
- периодические и финальные снимки счетчиков;
- транзакционное создание опроса вместе с вариантами ответа.

**Redis**

- дедупликация через `SET ... NX EX`;
- счетчики через `HINCRBY`;
- ограничение частоты по IP/подсети;
- кэш активного опроса;
- AOF и реплика в более серьезном окружении.

Redis здесь используется не просто как кэш: во время минутного эфира это оперативное хранилище приема голосов. Поэтому его недоступность должна приводить к явной ошибке `503`, а не к молчаливому обходу дедупликации.

## 4. Горячий путь голосования

1. Клиент получает случайный `device_id` в подписанной cookie. Если cookie нет, сервер создает ее.
2. API проверяет формат запроса, статус и временное окно опроса.
3. Из `device_id` вычисляется HMAC-хеш. Сырой идентификатор и IP не сохраняются.
4. По хешу выбирается одна из `N` корзин счетчиков.
5. Lua-скрипт в Redis атомарно:
   - создает dedup-key с `NX` и TTL до завершения опроса плюс небольшой запас;
   - при успехе увеличивает счетчики выбранных ответов;
   - при существующем ключе сообщает о повторном голосе.
6. API возвращает результат приема. Повторный голос можно считать корректно обработанным запросом с `accepted: false`, чтобы клиент не делал бессмысленные retry.

Пример ключей:

```text
dedup:{pollID:bucket}:<deviceHash>  -> 1, TTL
counts:{pollID:bucket}             -> hash(optionID => count)
rate:<ipHash>:<window>             -> counter, TTL
```

Часть в фигурных скобках — hash tag Redis Cluster. Dedup-key и счетчик одной корзины попадают в один slot, поэтому Lua-операция остается атомарной. Номер корзины вычисляется стабильно: `hash(deviceHash) % N`.

Шардированные счетчики важны: один `HINCRBY` на один ключ опроса создал бы hot key даже в Redis Cluster. Результат читается как сумма по всем корзинам. Для MVP можно использовать, например, 64 логические корзины даже на одном Redis — это оставляет понятный путь к кластеру.

### Надежность

Для тестового достаточно:

- Redis с AOF `appendfsync everysec`;
- периодический snapshot результатов в PostgreSQL;
- финализация после закрытия опроса;
- идемпотентная повторная финализация.

Это означает честно задокументированный риск потери примерно последней секунды данных при аварии Redis. Если потеря даже одного принятого голоса недопустима, нужен durable event log (например, Kafka) или синхронная запись события в надежное хранилище, что заметно расширяет задачу.

## 5. Базовая дедупликация и защита от накрутки

Абсолютно надежно запретить повторный анонимный голос невозможно. Без регистрации пользователь может удалить cookie, сменить браузер, IP или использовать скрипт. Это следует прямо написать, а не маскировать сложным fingerprinting.

Разумный базовый уровень:

- подписанная `HttpOnly`, `Secure`, `SameSite=Lax` cookie со случайным `device_id`;
- один голос на `(poll_id, device_hash)`;
- rate limit на IP или префикс подсети;
- общий rate limit на endpoint;
- простая проверка `Origin`/CORS и размера тела;
- опциональная CAPTCHA только после подозрительного поведения, а не для каждого зрителя.

Не стоит жестко запрещать один голос на IP: мобильные сети, офисы и домашние NAT дадут много ложных срабатываний. IP лучше использовать как мягкий сигнал и ограничитель скорости.

С точки зрения приватности:

- не сохранять сырой IP и User-Agent в таблице голосов;
- при необходимости использовать HMAC с серверным секретом;
- задать TTL техническим данным;
- описать, что результаты обезличены, но технические anti-abuse идентификаторы временно обрабатываются.

## 6. Модель данных

Минимальные таблицы:

```text
polls
- id UUID
- title
- type: single_choice | multiple_choice
- status: draft | active | closed
- starts_at, ends_at
- max_choices
- created_at, updated_at

poll_options
- id UUID
- poll_id FK
- text
- position

poll_result_snapshots
- poll_id FK
- option_id FK
- count BIGINT
- captured_at
- is_final
```

Если выбран вариант PostgreSQL-only, добавляется таблица `votes` с уникальным индексом `(poll_id, voter_hash)`. В рекомендуемом Redis-first MVP отдельные персональные голоса в PostgreSQL можно не хранить — только агрегаты.

Полезные инварианты:

- у активного опроса не меняются тип и варианты ответа;
- `starts_at < ends_at`;
- выбранные option IDs принадлежат указанному опросу;
- для `single_choice` передается ровно один вариант;
- для `multiple_choice` число вариантов находится в диапазоне `1..max_choices`;
- финальный результат неизменяем.

## 7. HTTP API

Возможный минимальный контракт:

```text
GET  /api/v1/polls/{slug}
POST /api/v1/polls/{id}/votes

POST /api/v1/admin/polls
POST /api/v1/admin/polls/{id}/publish
POST /api/v1/admin/polls/{id}/close
GET  /api/v1/admin/polls/{id}/results

GET  /health/live
GET  /health/ready
GET  /metrics
```

Пример запроса:

```json
{
  "option_ids": ["20cc4b69-04b6-46b1-8298-f9aec7721d83"]
}
```

Пример ответа:

```json
{
  "accepted": true
}
```

Для админки за два дня достаточно bearer token из переменной окружения или Basic Auth поверх TLS. Это лучше, чем оставить административные методы открытыми. Полноценные пользователи, refresh tokens и RBAC не относятся к ядру задания.

## 8. Локальный запуск и Linux

Предлагаемый набор контейнеров:

```text
api
postgres
redis
migrate
```

Команды, которые должны работать у проверяющего:

```bash
docker compose up --build
go test ./...
docker compose run --rm migrate up
k6 run tests/load/vote.js
```

Linux — естественный выбор:

- Go дает компактный статический бинарник и низкое потребление ресурсов;
- контейнер одинаково запускается локально и на сервере;
- Redis и PostgreSQL наиболее типично эксплуатируются именно в Linux-окружении;
- легко задать health checks, resource limits и graceful shutdown.

В Dockerfile стоит использовать multi-stage build, запуск от непривилегированного пользователя и минимальный runtime image. Конфигурация передается через environment variables, секреты не коммитятся.

Для самого тестового Docker Compose достаточен. Kubernetes manifests, Terraform и multi-region deployment без работающей необходимости будут выглядеть как лишний объем.

## 9. Проверка решения

### Unit-тесты

- правила `single_choice`/`multiple_choice`;
- временное окно опроса;
- расчет TTL;
- стабильный выбор корзины;
- обработка duplicate vote;
- переходы статусов.

### Integration-тесты

- создание опроса в PostgreSQL;
- атомарная дедупликация и инкремент в Redis;
- параллельная отправка одинакового голоса дает ровно один инкремент;
- суммирование результатов по корзинам;
- финализация в PostgreSQL;
- закрытый опрос не принимает голоса.

### Нагрузочный тест

k6-сценарий должен отдельно моделировать:

- много уникальных устройств;
- повторные запросы одного устройства;
- короткий ramp-up, минутный пик и спад;
- несколько вариантов ответа.

В отчете нужны не громкие заявления, а воспроизводимые числа для конкретного компьютера: RPS, p50/p95/p99, error rate, CPU/RAM API, Redis и PostgreSQL. Затем можно объяснить, что реальная емкость определяется только тестом production-подобного кластера.

## 10. Наблюдаемость

Минимально полезные метрики:

- `votes_accepted_total`;
- `votes_duplicate_total`;
- `votes_rejected_total{reason}`;
- latency HTTP p50/p95/p99;
- Redis errors/latency;
- число активных соединений и goroutines;
- возраст последнего snapshot;
- расхождение live и сохраненного результата.

Логи должны быть структурированными и содержать request ID, poll ID, статус и длительность, но не сырые IP, cookie и HMAC-хеш устройства.

## 11. Что реально сделать за два дня

### День 1

- структура проекта и конфигурация;
- схема БД и миграции;
- CRUD создания/получения опроса;
- прием голоса;
- Redis Lua script для дедупликации и счетчика;
- базовые unit-тесты.

### День 2

- получение live-результатов и финализация;
- admin auth;
- integration- и race-тесты;
- Dockerfile и Docker Compose;
- k6 smoke/load test;
- README, схема архитектуры и описание компромиссов;
- опционально минимальная страница голосования.

### Что сознательно не включать

- Kubernetes и Terraform;
- сложный RBAC;
- multi-region active-active;
- Kafka без реализованного consumer pipeline;
- ML-антифрод;
- красивую SPA в ущерб тестам backend;
- заявленную поддержку миллионов RPS без измерений.

Такой scope показывает Middle+ уровень лучше, чем большое количество заготовок: видны оценка нагрузки, корректная конкурентность, атомарность, приватность, эксплуатационные компромиссы и способность закончить задачу.

Слои стоит разделять по ответственности, но не строить чрезмерно абстрактную clean architecture. Для тестового достаточно явных interfaces у PostgreSQL/Redis и сервисов доменной логики.

## 13. Артефакты использования ИИ

Требование лучше выполнить явно. Например, добавить `docs/ai/README.md` со следующим:

- какие инструменты и модели использовались;
- исходные prompts или экспорт диалога;
- какие фрагменты были сгенерированы;
- что разработчик проверил и изменил вручную;
- какие предложения ИИ были отклонены и почему;
- команды тестов, которыми проверен результат.

Не следует коммитить секреты, персональные данные или локальные конфиги вместе с экспортом. Сам факт использования ИИ не заменяет инженерной ответственности: автор сдачи должен понимать Lua-скрипт, конкурентность и модель отказов и уметь объяснить их на собеседовании.

## Итоговая рекомендация

Я бы выбрал Go + PostgreSQL + Redis и запуск через Docker Compose на Linux. Это сильный и прагматичный вариант для двухдневного задания при трех условиях:

1. PostgreSQL остается долговременным источником истины, а Redis обслуживает горячий минутный интервал.
2. Инкремент и дедупликация выполняются атомарно; счетчики разбиты на корзины, чтобы не создавать один hot key.
3. В README честно разделены измеренная емкость MVP и production-дизайн для экстремального сценария.

Если хочется еще сильнее сократить реализацию, допустим PostgreSQL-only MVP с уникальным индексом и отдельным разделом о переходе на Redis. Но раз Redis уже предложен и характер нагрузки действительно bursty, рабочая Redis-first реализация будет наиболее убедительной частью решения.
